# ADR-010. Chrome 확장 대신 Electron 데스크탑 앱으로 만든다 (ADR-001·002·005 대체)

- 상태: 채택
- 날짜: 2026-09-07
- 대체: ADR-001(확장 선택), ADR-002(버블+iframe), ADR-005(핀 고정 엔진 탭)
- 영향: ADR-006(카카오 호스트)의 전달 수단만 변경, 결정 자체는 유지

## 맥락

2026-09-07 I-M0 측정에서 두 가지가 드러났다.

| 관찰 | 값 |
|---|---|
| 인스타 웹앱의 DM 읽기 | `graphql` 요청 (구 `/api/v1/direct_v2/` 미사용) |
| 인스타 웹앱의 DM 전송 | 웹소켓. 개발자 도구 본문 검색에서 보낸 문자열이 어떤 HTTP 요청에도 없음 |
| 구 REST 인박스 | **살아 있음.** 세션 쿠키 + `x-ig-app-id` 로 200 `application/json` |
| 실시간 소켓 | 5개(edge-chat 1 + gateway 4), 모두 문서 컨텍스트에서 열림 |

즉 읽기는 구 REST로 되지만, 전송은 웹앱과 같은 경로를 쓰려면 페이지가 연 소켓에
올라타야 한다. 확장에서는 이게 불리하다. 콘텐츠 스크립트는 격리된 세계에 있고,
MAIN world 훅은 페이지 스크립트보다 먼저 실행된다는 보장이 브라우저 정책에 묶여 있으며,
페이지 내부 함수를 직접 부르는 것은 확장 정책과 CSP 사이에서 취약하다.

동시에 사용자가 형태 자체를 바꾸기로 했다. **카카오톡 PC 앱처럼 브라우저 없이 혼자 뜨는
독립 창**이어야 하고, **Windows와 macOS를 모두** 쓰며, **카카오를 이번 범위에 포함**한다.

## 결정

**Electron 데스크탑 앱으로 만든다.**

1. 인스타 세션은 앱 안의 웹뷰(`BrowserView` + `partition: 'persist:instagram'`)가 보유한다.
   사용자는 그 웹뷰에서 평소처럼 로그인한다. 로그인 UI를 만들지 않는다는 ADR-004 원칙은 그대로다.
2. 웹뷰의 `preload`가 페이지 스크립트보다 먼저 실행되어 `window.WebSocket`을 감싼다.
   확장의 MAIN world 훅이 하려던 일과 같지만 제약이 없다.
3. 인스타 데이터는 그 웹뷰 컨텍스트에서 같은 오리진 `fetch`로 가져온다(구 REST, §9.1).
   쿠키는 브라우저가 붙인다. `sessionid`를 읽지 않는다는 NFR-03은 그대로다.
4. 카카오는 **기존 파이썬 호스트를 그대로** 쓴다. Electron 메인 프로세스가 자식 프로세스로
   띄우고 지금의 stdio 프레이밍·프로토콜로 이야기한다. Chrome 네이티브 메시징 등록
   (레지스트리, `allowed_origins`, `manifest.key`)이 통째로 사라진다.
5. UI는 지금 `panel.html/css/js`를 창 안으로 옮겨 재사용한다. 목록·대화·상태·필터 칩은
   그대로다.
6. **창은 하나다.** 목록과 대화를 한 창에서 오간다(2026-09-07 결정). 카톡 PC는 방마다 창을
   띄우지만, 우리는 지금 패널이 이미 그 방식이라 코드가 그대로 가고 창 관리 코드가 필요 없다.
   방별 창은 나중에 필요해지면 더한다.
7. **의존성 0 원칙은 여기서 끝난다.** ADR-009는 확장을 전제로 "번들러·프레임워크 없음"을
   지켰다. Electron 자체가 런타임 의존성이므로 `node_modules`가 생긴다. 다만 UI는 계속
   프레임워크 없이 직접 DOM으로 만들고, 런타임 의존성은 Electron 하나로 유지한다.

## 근거

- **오늘 잰 값이 그대로 유효하다.** Electron은 같은 크로미움이다. Tauri는 macOS에서
  WKWebView, Windows에서 WebView2를 쓰므로 엔진이 둘이 되고, 인스타가 다르게 동작할
  여지가 있으며 I-M0 측정을 두 번 해야 한다.
- **막힌 전송이 풀린다.** `preload`는 페이지보다 먼저 돌고 같은 컨텍스트에 접근할 수 있다.
  구 REST 전송이 되면 그걸 쓰고, 안 되면 페이지가 연 소켓·전송 함수에 올라탄다.
  확장에서는 후자가 사실상 불가능했다.
- **이미 만든 것을 버리지 않는다.** 파이썬 호스트(pytest 20)와 프로바이더 병합 로직
  (node 15), 패널 UI가 전부 그대로 간다. 네이티브 메시징 다리만 없어진다.
- **카카오가 단순해진다.** 브라우저 밖 앱이 브라우저 밖 앱을 제어하는 구조라 중간 다리가
  필요 없다. 설치 절차에서 레지스트리 등록이 빠진다.

## 결과

살아남는 것

| 대상 | 비고 |
|---|---|
| `panel.html/css/js` | 창 안으로 이동. 포트 통신만 IPC로 교체 |
| `poc/extension-provider/lib/providers.js` + 테스트 15 | 순수 로직, 그대로 |
| `poc/kakao-host/` 전체 + 테스트 20 | 그대로. 실행 방식만 네이티브 메시징 → 자식 프로세스 |
| `lib/native-port.js` | 프레이밍·요청 상관·백오프 로직 재사용, 연결 생성부만 교체 |
| `docs/01` 요구사항, `docs/04` §B 카카오 실험 | 그대로 유효 |
| `icons/` | 앱 아이콘으로 재사용 |

없어지는 것: `manifest.json`, `widget.js`, 콘텐츠 스크립트 주입, 플로팅 버블,
`chrome.storage.session`, 엔진 탭 관리, 네이티브 메시징 등록 스크립트의 레지스트리 부분.

새로 지는 부담

- 앱 용량이 크다(크로미움 동봉). 개인 사용이라 문제 삼지 않는다.
- 코드 서명과 자동 업데이트가 생긴다. 개인 사용이므로 서명 없이 로컬 설치로 시작한다.
- 웹뷰 세션 파티션을 디스크에 유지해야 로그인이 살아남는다.
- Windows와 macOS 두 대상에서 각각 빌드·검증해야 한다.

## 검토한 대안

- **Tauri:** 용량이 작고 시작이 빠르다. 그러나 플랫폼마다 웹뷰 엔진이 달라 인스타 동작
  보장이 약하고, 오늘 크로미움에서 잰 관찰을 다시 확인해야 한다. 기각.
- **확장 유지 + 화면만 카톡 PC식:** 전송 문제가 그대로 남고, 확장은 독립 창·항상 위·
  작업 표시줄 아이콘을 줄 수 없다. 기각.
- **데스크탑 앱 + 모바일 비공개 API:** ADR-001이 이미 기각했다. 정지 위험과 유지보수
  부담이 크다. 유지.
- **데스크탑 앱 + MQTT 직접 구현:** ADR-003이 v2로 미뤄 둔 것. 착수 조건은 그대로 둔다.

## 미결

- **인스타 전송 경로.** 구 REST `threads/broadcast/text/` 검증이 429로 중단됐다.
  이게 되면 전송도 HTTP로 끝난다. 안 되면 웹뷰 안 전송 경로에 올라탄다.
- **macOS 카카오.** 카톡 PC 제어는 Windows 어댑터만 있다. macOS는 별도 어댑터가 필요하고
  실기 실험(docs/04 §B)도 Windows에서만 가능하다.
