# ADR-004. 인증은 instagram.com 웹 세션을 그대로 쓴다 (로그인 UI 없음)

- 상태: 채택
- 날짜: 2026-09-07

## 맥락
요구사항 1번은 "계정 인증이 바로 되어야 한다"였다. 직접 로그인을 구현하면 아이디/비밀번호 입력, 2FA, 의심 로그인 챌린지, 기기 지문 문제를 모두 다뤄야 하고, 그 과정 자체가 봇처럼 보여 계정 정지 위험을 키운다.

## 결정
- 확장은 로그인 화면을 만들지 않는다. 사용자는 엔진 탭(instagram.com)에서 평소처럼 로그인한다.
- 로그인 여부는 `document.cookie`의 `ds_user_id` 존재로 판단한다. `sessionid`(HttpOnly)는 읽지 않고 읽을 수도 없다.
- 인스타 요청은 엔진 탭의 콘텐츠 스크립트에서 같은 오리진 fetch로만 보낸다. 쿠키는 브라우저가 자동으로 붙인다. CSRF 헤더용 `csrftoken`만 쿠키에서 읽는다.
- 세션 만료(401/403, 로그인 페이지 리다이렉트, JSON 아닌 응답)를 `logged_out`으로 감지하고, 패널 배너의 [인스타그램 열기]로 엔진 탭을 앞으로 가져온다. 로그인 후에는 폴백 폴링이 성공하는 순간 자동 복구된다.

## 근거
- 인증 작업이 0이며 2FA·챌린지도 인스타 UI가 처리한다.
- 쿠키를 추출·저장·전송하지 않으므로 유출 면적이 없다.
- mautrix-meta 등 검증된 오픈소스도 같은 방식(웹 세션 쿠키)을 쓴다.

## 결과
- 장점: 요구사항 1번을 코드 없이 만족. 정지 위험이 웹 수준.
- 단점: instagram.com 탭이 반드시 하나 있어야 한다(ADR-005). 세션이 만료되면 사용자가 인스타 탭에서 다시 로그인해야 한다.

## 검토한 대안
- 아이디/비밀번호 로그인 구현(비공개 API): 챌린지·정지 위험, 구현 부담. 기각.
- 쿠키를 추출해 background에서 요청: 쿠키 파티셔닝·헤더 위조 문제, 유출 면적 증가. 기각.
