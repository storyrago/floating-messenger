# ADR-003. 실시간 갱신은 WebSocket 프레임 "신호" + inbox 재조회로 한다 (프로토콜 미해석)

- 상태: 채택 (v2에서 재검토 조건 명시)
- 날짜: 2026-09-07

## 맥락
인스타 웹은 MQTT over WebSocket(LightSpeed 계열) 실시간 채널을 쓴다. 페이로드를 직접 해석하면 재조회 없이 메시지를 만들 수 있지만, 프로토콜 분석과 지속적 유지보수가 필요하다. 반대로 단순 폴링은 지연이 폴링 주기만큼 생겨 "웹보다 빠르다"는 목표에 못 미친다.

## 결정
- `hook.js`(MAIN world)가 `window.WebSocket`을 Proxy로 감싸 실시간 소켓의 `message` 이벤트마다 "프레임 도착" 신호만 보낸다. 페이로드는 읽지 않는다.
- `ig-bridge.js`는 신호를 300ms 디바운스한 뒤 inbox 엔드포인트를 재조회한다. 최소 간격 500ms, 429 쿨다운, 15초 폴백 폴링을 둔다.
- MQTT/LightSpeed 파싱은 v2 항목으로 두고, 착수 조건을 정한다: v1 측정에서 `recv→render` p50이 목표(800ms)에 미달하고 병목이 재조회 왕복임이 확인될 때.

## 근거
- 신호만으로도 "도착 후 재조회 1회 왕복" 수준의 지연(수백 ms)이라 목표 안에 든다.
- 프로토콜 변경에 거의 영향받지 않는다. 소켓 호스트 정규식 하나만 관리한다.
- 타이핑 표시 등 잡음 프레임은 디바운스와 최소 간격으로 흡수된다.
- 재조회는 웹 클라이언트도 쓰는 엔드포인트라 트래픽이 자연스럽다.

## 결과
- 장점: 구현·유지보수 부담이 작다. 인스타 응답 정규화 계층만 관리하면 된다.
- 단점: 메시지당 fetch 1회가 추가된다. 활발한 대화에서 초당 최대 2회로 제한된다. 소켓이 Worker에서 열리면 훅이 무력화되어 폴백 폴링(15초)만 남는다(C4).

## 검토한 대안
- 단순 폴링(2~3초): 구현 가장 쉬움, 지연이 커서 목표 미달. 폴백으로만 채택.
- 엔진 탭 DOM 관찰(MutationObserver): 프로토콜 무관하지만 인스타 렌더링 지연을 그대로 상속해 웹보다 빠를 수 없음. 기각.
- MQTT/LightSpeed 직접 파싱(mautrix-meta 참고): 가장 빠르지만 유지보수 비용이 큼. v2로 보류.
