# ADR-011. 범위를 인스타그램 하나로 줄인다 (ADR-006·008 대체, ADR-007 범위 수정)

- 상태: 채택
- 날짜: 2026-09-07
- 대체: ADR-006(카카오 네이티브 호스트), ADR-008(카카오 수신 경로)
- 수정: ADR-007의 "여러 메신저를 프로바이더로 붙이는" 범위

## 맥락

두 가지가 겹쳤다.

**하나. 배포 의사.** 지금은 본인과 친구가 쓰지만, 나중에 다른 사람도 쓰게 하고 싶다는
방향이 나왔다. 그 방향에서 카카오는 어느 경로로도 성립하지 않는다.

| 경로 | 상태 |
|---|---|
| 카카오 공식 API로 대화 수신 | **없다.** 로그인 API는 있지만 받은 메시지를 읽는 API가 없다(ADR-006 F3) |
| 카카오톡 채널·상담톡 | 비즈니스 계약 제품. 셀프서비스 연동이 아니다 |
| PC 앱 제어(현재 설계) | 사용자 PC의 알림을 통째로 읽고 창을 조작한다. 남에게 배포할 수 없다 |

**둘. 실기 검증을 못 한다.** 개발 머신이 macOS다. 카카오 어댑터는 알림 리스너와 창 제어가
모두 Windows 전용이라 K-P1 실험(docs/04 §B) E0~E5를 시작조차 못 했다. 즉 지금까지 카카오는
mock 어댑터로만 돌았고, 실제로 동작한다는 증거가 하나도 없다.

정리하면, 배포 가능성이 없고 검증도 못 한 트랙이 코드와 문서의 절반을 차지하고 있었다.

## 결정

**인스타그램 하나만 만든다.** 카카오 프로바이더와 그에 딸린 모든 것을 저장소에서 지운다.

지우는 것

| 대상 | 내용 |
|---|---|
| `poc/kakao-host/` | 파이썬 호스트, 어댑터, 실험 스크립트, 설치 스크립트, pytest 20 |
| `poc/extension-native-echo/` | Chrome↔호스트 왕복 검증용 확장 |
| `poc/extension-provider/` 의 카카오 부분 | `applyKakaoItem`, `optimisticKakaoItem`, `PROVIDERS.kakao`와 해당 테스트 |
| `host/` | M5에 호스트를 승격하려던 빈 디렉터리 |
| 앱 코드의 카카오 흔적 | `app/main.js` MOCK의 카카오 스레드, `panel.js`·`panel.css`의 카톡 라벨과 색 |

남기는 것

- **`provider:id` 네임스페이스와 `capabilities` 게이팅은 유지한다.** 프로바이더가 하나뿐이라
  당장은 값이 없지만, 지우면 `panel.js`의 id 처리와 렌더링을 함께 건드려야 한다. 두 줄을
  남겨 두는 쪽이 지금 diff가 작다. 나중에 다른 메신저를 붙일 여지도 남는다.
- **파이썬 호스트 코드는 git 이력에 남는다.** 되살릴 일이 생기면 `git log` 로 꺼낸다.

## 근거

- 검증되지 않았고 배포도 불가능한 트랙을 안고 가면, 인스타 쪽 작업을 할 때마다 카카오
  분기와 문서를 함께 손봐야 한다. 그 비용이 매번 든다.
- 카카오를 되살릴 조건이 명확하다. Windows 개발 환경이 생기고, 배포를 포기하고 개인
  도구로만 쓰기로 확정될 때다. 그때 이력에서 꺼내면 된다.

## 결과

- 문서에서 카카오 부분(docs/01 FR-15~18, docs/02 §8·§9.2, docs/03 K-P0·K-P1·M5·M6,
  docs/04 §B·§C)은 **이 ADR로 무효가 된다.** 각 문서를 통째로 다시 쓰지 않고 상태 줄에서
  이 ADR을 가리킨다. 원문은 당시 판단의 기록으로 남긴다.
- `npm run verify` 에서 `test:host`(pytest)가 사라진다. 파이썬 의존성이 없어진다.
- 필터 칩은 프로바이더가 하나라 자동으로 숨는다(`panel.js`가 이미 그렇게 동작한다).
- 프로젝트 이름 `floating-messenger`와 코드네임 `buoy`는 그대로 둔다(ADR-007). 메신저
  이름이 안 들어간 이름이라 범위가 줄어도 맞지 않게 되지 않는다.

## 배포에 대한 메모

이 결정은 "인스타 전용 개인 도구"까지다. 모르는 사람에게 배포하는 단계는 이 구조로 갈 수
없다. 앱 안 웹뷰에 비밀번호를 치게 하는 구조라 사용자가 진위를 확인할 방법이 없고, 비공식
엔드포인트 사용은 사용자 계정의 정지 위험을 사용자에게 지운다. 그 단계로 가려면 공식
Instagram 메시징 API(프로페셔널 계정 + 앱 심사 + 웹훅 서버)를 쓰는 **별도 프로젝트**를
시작해야 한다. 웹훅이 서버로 오기 때문에 데스크탑 앱 구조와 공유할 코드가 화면 정도뿐이다.
